ТЕКСТ ДЛЯ ЗАЩИТЫ ПРЕЗЕНТАЦИИ «UEFI-BOOTLOADER»

Слайд 1. UEFI-BOOTLOADER

Здравствуйте. Мы представляем проект UEFI-загрузчика и собственного ядра. 


Слайд 2. Главная идея

Основная идея проекта заключается в том, чтобы пройти полный путь от запуска UEFI-приложения до передачи управления собственному коду ядра. Глобально можно поделить на 5 шагов:

1. UEFI запускает наш загрузчик.
2. Загрузчик собирает информацию о системе.
3. Загрузчик выходит из Boot Services.
4. Kernel получает управление.
5. Kernel сам работает с framebuffer.


Слайд 3. Структура проекта

Проект разделён на две основные части: LabExitBs, который работает до ExitBootServices и mini-kernel ядро, которое работает после ExitBootServices.

LabExitBs — это UEFI-загрузчик. Он собирается через edk2 как обычное UEFI-приложение формата .efi. Его задача — стартовать в UEFI-среде, получить нужные протоколы, собрать данные о системе, завершить Boot Services и передать управление ядру.

Вторая часть — mini-kernel. Это бинарник, который загрузчик копирует в память и запускает вручную. 


Слайд 4. LabExitBs как UEFI-загрузчик

LabExitBs стартует как UEFI-приложение. Пока он работает до ExitBootServices, он может обращаться к UEFI Boot Services и использовать UEFI-протоколы. Так как после вызова ExitBootSevices управление полностью передается ядру, то нам необходимо получить информацию о системе.

Первая важная задача LabExitBs — получить GOP, Graphics Output Protocol. GOP нужен для работы с графическим выводом. Через него загрузчик получает адрес framebuffer, ширину и высоту экрана. Эти значения потом сохраняются в SystemInfo, чтобы mini-kernel мог рисовать напрямую в видеопамять. gBS — это глобальный указатель на UEFI Boot Services. LocateHandleBuffer ищет все UEFI handle'ы, которые поддерживают указанный протокол. То есть код говорит: UEFI, найди мне все устройства, которые поддерживают Graphics Output Protocol. LocateHandleBuffer дал только список handle'ов. Чтобы реально работать с GOP, нужен указатель на сам протокол. gBS->HandleProtocol(...) Он говорит: Для данного handle дай мне интерфейс Graphics Output Protocol.

Вторая важная задача — получить MP Services. MP Services — это UEFI-протокол для работы с несколькими процессорами на этапе Boot Services. В нашем случае через него загрузчик узнаёт, сколько процессоров доступно, и получает их APIC ID. APIC ID — это идентификатор процессора, который используется при работе с Local APIC и запуске AP-процессоров. Сперва вызывается функция, которая должна найти и подготовить MP Services. Далее context_processors_count(&ctx) получает количество процессоров, доступных в системе. Затем в цикле загрузжчик проходит по всем процессорам и получает информацию о конкретном CPU. И печатаем информацию в UEFI Shell.

Затем LabExitBs формирует структуру SystemInfo. Эта структура является мостом между UEFI-загрузчиком и mini-kernel. В неё записываются video.buffer, video.width, video.height, processors.size и processors.ids[]. После ExitBootServices kernel уже не сможет обратиться к GOP или MP Services, поэтому SystemInfo должна быть полностью подготовлена заранее. 


Слайд 5. LabExitBs: переход от UEFI к kernel

На этом слайде показан момент перехода от UEFI к mini-kernel.

Сначала загрузчик получает memory map через GetMemoryMap. Карта памяти - список всех областей физической памяти компьютера на момент загрузки. Memory map нужен для корректного вызова ExitBootServices. В UEFI ExitBootServices требует актуальный MapKey, который возвращается функцией GetMemoryMap. MapKey — это ключ версии карты памяти. MapKey подтверждает, что карта памяти, которую видел загрузчик, всё ещё актуальна. Если карта памяти изменилась после получения MapKey, вызов ExitBootServices может завершиться ошибкой, поэтому загрузчик должен получить актуальную карту памяти непосредственно перед выходом.

После этого вызывается ExitBootServices. Это означает, что UEFI Boot Services завершают работу, и управление платформой фактически переходит к нашему коду. После этого нельзя использовать Print, LocateProtocol, AllocatePool, OpenProtocol и другие Boot Services.

Дальше LabExitBs копирует встроенный массив kernel[] в физическую память по адресу 0x2000. Этот адрес выбран как точка входа mini-kernel. kernel[] появляется внутри LabExitBs благодаря тому, что бинарник mini-kernel заранее был преобразован в kernel.inc через xxd -i.

Затем загрузчик передаёт указатель на SystemInfo через регистр RAX. Это простой способ передать данные от загрузчика в kernel. В конце LabExitBs выполняет jmp 0x2000. С этого момента управление уже не возвращается в UEFI-загрузчик, а начинает выполняться код mini-kernel.


Слайд 6. Mini-kernel

Mini-kernel — собственный код. Он уже рабоатет после ExitBootServices, соответственно он не может уже взаимодействаовать с Uefi - функциями. Всё, что ему нужно, он должен либо получить от загрузчика заранее, либо реализовать самостоятельно.

Основная задача mini-kernel — показать, что после ExitBootServices код может работать самостоятельно: получать данные из SystemInfo, обращаться к Local APIC, рисовать символы и строки напрямую во framebuffer.


Слайд 7. Сборка mini-kernel

Mini-kernel собирается отдельно. Его нужно собрать как бинарник, который затем можно скопировать в память и выполнить вручную.

В сборке участвует Makefile. Сначала processor_init.nasm собирается в бинарный файл processor_init. Это код для AP-процессоров. Затем этот бинарник преобразуется в processor_init.inc через xxd -i, чтобы его можно было подключить в main.c как массив байтов.

Далее запускается font-gen.py. Этот скрипт генерирует font.inc — bitmap-шрифт, который kernel использует для вывода символов во framebuffer. Это нужно потому, что после ExitBootServices у kernel нет системных шрифтов и нет UEFI Print.

После этого entry.nasm собирается в entry.o. main.c компилируется в объектный код. Затем всё линкуется в kernel.elf. При линковке используется linker.lds. Linker script задаёт порядок секций и гарантирует, что секция .entry с точкой входа находится в начале образа. Это важно, потому что загрузчик просто копирует бинарник в 0x2000 и прыгает в начало. Секция .text — это область, куда кладётся исполняемый код и read-only данные. KEEP(*(.entry)) здесь обеспечивается, что код из entry.nasm попадёт в начало итогового kernel.

После получения kernel.elf выполняется objcopy -O binary, который превращает ELF-файл в сырой бинарник kernel. Именно этот kernel затем превращается в kernel.inc через xxd -i и встраивается в LabExitBs.


Слайд 8. entry.nasm — вход в kernel

entry.nasm — это первая точка выполнения mini-kernel после перехода загрузчика на адрес 0x2000. Его задача — подготовить минимальное окружение перед вызовом main().

Когда LabExitBs выполняет jmp 0x2000, в регистре RAX находится указатель на SystemInfo. Поэтому entry.nasm сначала проверяет RAX. Если RAX не равен нулю, это означает, что управление пришло от BSP, то есть основного процессора, запущенного загрузчиком. В этом случае entry.nasm сохраняет RAX в глобальную переменную info.

Далее entry.nasm настраивает стек. В проекте для BSP используется стек по адресу 0x100000. Стек нужен, потому что дальше будет вызван C-код main(), а C-код использует стек для локальных переменных, возвратов из функций и передачи части данных.

После сохранения info и настройки стека entry.nasm вызывает main(). Если main() когда-либо вернётся, код уходит в бесконечный цикл.

Также в entry.nasm есть проверка RAX на ноль. Это связано с тем, что при запуске AP-процессоров они приходят в kernel с RAX = 0, чтобы не перезаписать глобальный указатель info.


Слайд 9. main.c — основной код ядра

main.c — это основной код после входа через entry.nasm. 

У нас SystemInfo является мостом между LabExitBs и mini-kernel. Загрузчик заранее заполняет эту структуру до ExitBootServices, а mini-kernel потом использует её уже без обращения к UEFI. В SystemInfo есть два основных блока: video и processors.

Блок video содержит адрес framebuffer, ширину и высоту экрана. Блок processors содержит количество процессоров и массив APIC ID. 

Глобальная переменная SystemInfo *info заполняется в entry.nasm. Поэтому main.c не получает параметры обычным способом вместо этого он работает с глобальным указателем, который был передан через RAX и сохранён на этапе входа в kernel.


Слайд 10. Механизм запуска AP-процессоров

На этом слайде показан механизм запуска дополнительных процессоров, или AP-процессоров. В x86-системах один процессор является BSP — Bootstrap Processor. Именно он первым получает управление. Остальные процессоры называются AP — Application Processors. Чтобы они начали выполнять наш код, BSP должен запустить их вручную.

Для этого используется Local APIC. Local APIC — это контроллер прерываний, связанный с конкретным процессором. Через его регистры можно отправлять межпроцессорные прерывания, в том числе INIT и SIPI. INIT переводит AP в начальное состояние, а SIPI задаёт вектор старта.

Функция get_self_apic_id читает регистр Local APIC по адресу 0xFEE00020. В старших битах этого регистра находится APIC ID текущего процессора (поэтому значение сдвигается вправо на 24 бита). Этот ID используется, чтобы понимать, какой процессор сейчас выполняет код.

Функция start_ap() запускает один конкретный AP-процессор. Она работает через ICR - это регистр Local APIC, через который один процессор может отправить команду другому процессору. У него две части: 0xfee00300 — ICR low - задаёт, какую команду отправить. 0xfee00310 — ICR high - задаёт, какому процессору отправить команду. APIC ID получателя записывается в старший байт ICR high. Далее мы отправляем INIT IPI - сигнал инициализации AP-процессора, т.е. BSP говорит AP: подготовься к старту. Потом уже отправляем SIPI - команда запуска AP с определённого физического адреса.

Функция startup_processors копирует processor_init в память по адресу 0x1000. Это нужно потому, что AP после SIPI стартуют с адреса, вычисляемого как SIPI vector умножить на 0x1000. В проекте init_code_entry равен 0x1000, значит vector = 0x1000 >> 12 = 1, и AP начинают выполнение с адреса 0x1000.

Затем BSP считывает CR3 — специальный регистр процессора, который показывает адрес текущих таблиц страниц (Таблицы страниц — это структура в памяти, по которой процессор переводит адреса, т.к. у нас виртуальный адрес — адрес, который использует код, физический адрес — реальный адрес в оперативной памяти. Таблицы страниц говорят процессору: виртуальный адрес X соответствует физическому адресу Y ) — и записывает его в конец trampoline-кода. Также туда записывается entry point kernel, то есть 0x2000. После этого BSP проходит по списку APIC ID и вызывает start_ap для каждого AP.


Слайд 11. processor_init.nasm

processor_init.nasm — это стартовый код для AP-процессоров. Он нужен потому, что AP после сигнала SIPI не стартует сразу в готовом 64-битном окружении main.c. Ему нужно пройти низкоуровневую инициализацию режима процессора.

AP начинает выполнение по адресу 0x1000 (org 1000h) в 16-битном режиме (use16). В начале processor_init отключает прерывания (cli), загружает временную GDT (GDT — это таблица, где описано, какие сегменты кода и данных есть у процессора) и включает protected mode. GDT нужна для описания сегментов кода и данных, которые будут использоваться при переходе между режимами.

Временная GDT Здесь описаны сегменты: 
1. нулевой сегмент — обязательный пустой descriptor; 
2. 32-битный сегмент кода;
3. сегмент данных;
4. 64-битный сегмент кода;
5. 64-битный сегмент данных.

После перехода в 32-битный protected mode код включает PAE (устанавливаем 5 бит) через CR4 - управляющий регистр процессора, загружает CR3, который BSP заранее записал, чтобы AP получил те же таблицы страниц, которые использует BSP, затем включает long mode через MSR EFER (Адрес 0xC0000080), устанавливая бит LME (Бит 8 в EFER — это LME, Long Mode Enable). После этого включается paging через CR0.PG (т.е. AP включает страничную адресацию, необходимую для 64-битного режима), и выполняется far jump в 64-битный код.

В 64-битной части processor_init настраивает сегментные регистры, читает APIC ID текущего AP через Local APIC, вычисляет отдельный стек для AP по формуле 0x100000 + APIC_ID * 4096 (каждому процессору выделяется отдельная область стека размером 4 KiB), устанавливает rsp и rbp, затем берёт entry_point и выполняет far jump.

Важно, что перед переходом в kernel код обнуляет RAX. Это сделано для того, чтобы AP не перезаписали SystemInfo в entry.nasm. BSP приходит в kernel с RAX = SystemInfo*, а AP приходят с RAX = 0.


Слайд 12. Работа с framebuffer, прямой вывод на экран

После ExitBootServices mini-kernel больше не может использовать UEFI Print. Поэтому для вывода текста была реализована работа напрямую с framebuffer. Framebuffer — это область памяти, где каждый элемент соответствует пикселю на экране.

Адрес framebuffer, ширина и высота экрана заранее получаются загрузчиком через GOP и передаются в SystemInfo. В main.c эти данные доступны через info->video.buffer, info->video.width и info->video.height.

Функция screen_clear очищает экран. Она получает высоту и ширину из info->video, получает указатель на framebuffer как volatile u32* (b - указатель на массив 32-битных значений, т.е. один элемент массива b = один пиксель экрана, volatile говорит компилятору: не оптимизируй обращение к этой памяти, каждая запись должны реально выполниться), а затем двумя циклами проходит по всем пикселям и записывает в каждый выбранный цвет.

Функция screen_set_pixel отвечает за установку одного пикселя. Так как framebuffer рассматривается как одномерный массив, координаты x и y переводятся в индекс по формуле y * width + x. После этого по этому индексу записывается 32-битное значение цвета.

Функция screen_draw_char уже строится поверх screen_set_pixel. Она не работает напрямую с текстовой консолью, а рисует символ как набор пикселей.


Слайд 13. Отрисовка символа через font-gen.py и font.inc

Так как mini-kernel работает без UEFI Print и без системных шрифтов, шрифт нужно подготовить заранее. Для этого используется font-gen.py. Этот скрипт генерирует bitmap-шрифт - тип шрифта где каждый символ представлен фиксированной матрицей пикселей и сохраняет его в font.inc.

font.inc подключается прямо в main.c. В нём определены FONT_WIDTH и FONT_HEIGHT. В текущей реализации ширина символа равна 16 пикселям, а высота — 24 пикселя. Один символ занимает 16 на 24, то есть 384 бита. Это 48 байт на символ.

Каждый символ хранится как массив битов. Если бит равен 1, соответствующий пиксель символа должен быть закрашен. Если бит равен 0, пиксель пропускается, и фон остаётся чёрным.

Функция screen_draw_char получает символ c, берёт font[c], затем проходит двумя циклами по высоте и ширине символа. Для каждой позиции вычисляется номер бита: n = i * FONT_WIDTH + j. После этого определяется байт n / 8 и номер бита n % 8. Если бит установлен, вызывается screen_set_pixel с координатами x + j и y + i.


Слайд 14. Вывод строки и многострочного текста

После того как реализована отрисовка одного символа, следующий шаг — вывод строки. Для этого используется функция screen_draw_string. Она идёт по символам строки до завершающего нуля, каждый символ выводит через screen_draw_char, а координату x после каждого символа увеличивает на FONT_WIDTH. Так символы располагаются слева направо.

Фрагмент про новую реализацию рассказываю от себя.

Но для status panel одной строки недостаточно. Нужно уметь выводить несколько строк. Поэтому была реализована функция screen_draw_text. Она работает почти так же, как screen_draw_string, но дополнительно обрабатывает символ переноса строки '\n'.

Когда screen_draw_text встречает обычный символ, он рисует его и увеличивает x. Когда встречается '\n', x возвращается к начальному значению start_x, а y увеличивается на FONT_HEIGHT + TEXT_LINE_GAP. Это позволяет перейти на следующую строку.

Благодаря этому status panel можно собрать как один большой многострочный текст и вывести одним вызовом screen_draw_text. Это важное архитектурное решение: вместо множества отдельных вызовов отрисовки каждая строка сначала попадает в общий status_buffer, а затем весь буфер выводится на экран один раз.

Такой подход оказался более стабильным и понятным для bare-metal mini-kernel.


Слайд 15. Сборка status_buffer

На этом слайде показано, как формируется текст финальной status panel. В проекте используется буферная схема вывода. Это значит, что текст сначала собирается в массив status_buffer, а потом одним вызовом выводится через screen_draw_text.

status_buffer — это обычный массив char фиксированного размера. В него последовательно добавляются символы, строки, десятичные числа и hex-адреса. Для этого внутри build_kernel_status_buffer используются макросы.

BUF_PUTC добавляет один символ в буфер и следит, чтобы позиция не вышла за STATUS_BUFFER_SIZE. После добавления символа он также ставит завершающий ноль, чтобы буфер всегда оставался корректной C-строкой.

BUF_PUTS добавляет строку посимвольно, вызывая BUF_PUTC для каждого символа. Так как в mini-kernel нет printf и стандартной библиотеки, вывод строк и чисел реализован вручную.

BUF_PUT_DEC преобразует число в десятичный вид. Например, ширина экрана 1280 преобразуется в символы '1', '2', '8', '0'. Сперва ищем старший десятичный разряд, затем по очереди добавляем цифры в буфер ("0" + digit потому что символы в ASCII идут подряд так число превращается в текстовый символ, т.е. "0" = 48 "1" = 49 и тд. если нам нужен символ "5" то мы деалем "0" + 5 = 48 + 5 = 53 = "5"). BUF_PUT_HEX выводит 64-битные адреса в шестнадцатеричном формате, например адрес framebuffer, SystemInfo или архитектурные адреса 0x1000 и 0x2000. Одна hex-цифра соответствует 4 битам, если у нас 64-битное число, его можно разбить на 16 кусочков по 4 бита поэтому делаем такой цикл for (int shift = 60; shift >= 0; shift -= 4), каждая итерация берёт следующую hex-цифру слева направо, (value >> shift) эта часть сдвигает нужную hex-цифру в самый конец числа, & 0xF оставляет только последние 4 бит, т.е. (value >> shift) & 0xF означает: сдвинуть нужную hex-цифру вправо и оставить только её одну. Если digit от 0 до 9, его можно превратить в символ цифры: BUF_PUTC((char)('0' + digit)); else если digit от 10 до 15, это hex-буквы.

В результате build_kernel_status_buffer формирует готовый текстовый отчёт о состоянии kernel. Затем main вызывает screen_draw_text и выводит весь буфер на экран.


Слайд 16. Status panel

Финальная status panel показывает диагностическую информацию, которую kernel получил от загрузчика и сам определил во время выполнения.

Текст панели собирается в status_buffer. Вывод выполняется одним вызовом screen_draw_text. Данные берутся из SystemInfo и Local APIC. Адреса выводятся в hex через BUF_PUT_HEX, а размеры экрана и количество CPU выводятся в decimal через BUF_PUT_DEC.

На панели отображаются ключевые адреса проекта. KERNEL ENTRY — это 0x2000, адрес, куда загрузчик копирует kernel и куда выполняет jmp. AP TRAMPOLINE — это 0x1000, адрес, куда копируется processor_init для запуска AP. BSP STACK — это 0x100000, адрес стека BSP.

Далее выводятся реальные данные текущего запуска: SYSTEMINFO — адрес структуры SystemInfo; FRAMEBUFFER — адрес видеобуфера; WIDTH и HEIGHT — разрешение экрана; CPU COUNT — отношение реально активных в текущей status panel CPU к общему количеству найденных CPU.

В финальной версии AP startup отключён, поэтому AP STARTUP показывает DISABLED, а CPU COUNT имеет вид 1/N. Это означает, что status panel выполняет только BSP, а N — это общее количество процессоров, которое загрузчик получил через MP Services. Также выводятся BSP APIC ID и список APIC IDs.


Слайд 17. Выводы и демонстрация

В результате работы был реализован UEFI-загрузчик LabExitBs и собственный mini-kernel. LabExitBs запускается как UEFI-приложение, получает GOP, MP Services и memory map, формирует SystemInfo, вызывает ExitBootServices и передаёт управление kernel.

После ExitBootServices управление передаётся mini-kernel, который находится по адресу 0x2000. Указатель на SystemInfo передаётся через RAX. entry.nasm сохраняет этот указатель, настраивает стек и вызывает main.c.

Mini-kernel работает без UEFI Boot Services. Это значит, что для вывода он не использует Print, а работает напрямую с framebuffer. Для этого были реализованы функции очистки экрана, установки пикселя, вывода символа, строки и многострочного текста.

Также была добавлена буферная status panel. Текст панели собирается в status_buffer, числа переводятся в decimal и hex вручную, без printf. Затем весь буфер выводится на экран одним вызовом screen_draw_text.

Kernel отображает информацию о framebuffer, разрешении экрана, количестве процессоров, APIC ID и ключевых адресах проекта. Механизм запуска AP-процессоров также реализован и сохранён в коде, но в финальной status panel отключён, чтобы вывод выполнялся только BSP и не было конкурентной записи во framebuffer.

Главный результат проекта — демонстрация полного перехода от UEFI-среды к собственному bare-metal kernel-коду, который после ExitBootServices самостоятельно работает с памятью, процессорами и видеобуфером.
